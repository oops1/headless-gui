# Прототип модели рендера Р5–Р8: отчёт (задача 4.3)

Дата: 2026-10-28. Ветка `feature/engine-architecture`, стенд —
`engine/renderproto_test.go` (тесты и бенчмарки, в релиз не входит).
Основание — `docs/ARCHITECTURE_REVIEW_RU.md` §4.6: решение по Р5–Р8
принимается по прототипу, не по оценке. Решение — за владельцем (задача 4.4).
Стенд и отчёт прошли состязательное ревью (методика, корректность стенда);
29 замечаний учтены, цифры ниже — после исправлений.

## Что построено

Четыре изменения модели рендера, собранные в измерительный стенд поверх
сегодняшнего холста (`core/raster`), без правок движка:

| # | Что | Как в прототипе |
|---|---|---|
| Р5 | `Draw` пишет команды, а не пиксели | `protoRecorder` — `DrawContext` со всеми необязательными возможностями (кроме `Snapshotter`, см. риски); измерения отдаёт настоящему холсту; каждая команда хранит аргументы, действовавший клип (прямоугольный и скруглённый) и логический охват |
| Р6 | Растеризация по тайлам 64×64 в пуле | команды раскладываются по тайлам по охвату; каждый изменившийся тайл — часть `workpool.Run`; воркер рисует в свой холст размером с тайл через сдвигающий контекст (`translatingContext`), клип переключается только при смене |
| Р7 | Дифф по хэшу команд на тайл | FNV-1a по аргументам команды (картинки — по адресу и поколению `InvalidateImageCache`), хэш тайла — свёртка хэшей его команд по порядку; тайл с прежним хэшем не рисуется и не сравнивается; без изменившихся тайлов пул не трогается |
| Р8 | Один полный буфер | у кадра один буфер `front`; тайл сравнивается с ним прямо из холста воркера и копируется, только если отличается |

Команды, читающие пиксели кадра за пределами своего участка (`BlurBehind`;
в стенде так же ведёт себя `DrawNoise`, см. ниже), делят кадр на сегменты:
сегменты до и после идут по тайлам через полный рабочий буфер, сама команда
— на нём же одной горутиной, дифф — рабочего буфера с `front`, как сегодня.
**В таком кадре Р7 и Р8 не действуют**: все тайлы всех сегментов рисуются,
буферов снова два.

Тождественность (`TestRenderProto_*`): кадр по новой модели **побайтно
равен** кадру движка на обеих сценах — текстовая `benchTextScene` 1280×800
(180 лейблов, 182 команды) и рабочий стол `buildPipelineDesktop` 1280×800
(тема Windows 11, 159 команд, одна читающая — `BlurBehind` панели задач);
с личными видами шрифта у воркеров; после кадра с размытием следующий без
него; изменение одного лейбла перерисовывает только его тайлы, и кадр без
изменений не рисует ни одного тайла.

## Измерения

Машина: 20 логических процессоров, Go 1.27, `go test -bench -count=6`,
медианы benchstat. Сегодняшние числа — те же бенчмарки движка в том же
прогоне. В «сегодня» входит обход дерева (`DrawTraced`), фон, дифф и
классификация тайлов; у прототипа пара «запись + растр» включает обход
дерева и запись команд, пара «растр» — только раскладку, растр и сравнение
по готовому списку.

### Полный кадр (Р6)

| Сцена | Сегодня | Прототип: запись + растр | Прототип: только растр |
|---|---|---|---|
| Текст 1280×800 (`RenderFrameFull`) | 2,02 мс | **0,63 мс** (`ProtoRecordTiledOwnFonts_Text`), ×3,2 | 0,38 мс (`ProtoTiledOwnFonts_Text`) |
| то же, воркеры делят один вид шрифта | 2,02 мс | 3,46 мс (`ProtoRecordTiled_Text`) | 2,96 мс (`ProtoTiled_Text`) |
| то же, одна горутина | 2,02 мс | — | 2,97–3,01 мс (`ProtoTiledSerial*`) |
| Рабочий стол 1280×800 (`Pipeline_FullFrame`) | 2,55 мс | **1,37 мс** (`ProtoRecordTiled_Desktop`), ×1,9 | 1,29 мс (`ProtoTiled_Desktop`) |

Р6 подтверждён с условием: полный кадр дешевле в 2–3 раза, но только если
воркеры **не делят один вид шрифта** (`FontCache`). Замок вида между 20
воркерами съедает параллелизм целиком: с общим видом тайловый кадр дороже
сегодняшнего. Общий кэш растров 4.2 делает личные виды дешёвыми: у воркера
свой `FontCache` с тем же составом шрифтов, что у холста движка (основной,
ленивые запасные, встроенные начертания — путь отрисовки тот же), маски — из
общего L2, растеризуются один раз на процесс.

Одной горутиной тайловый кадр текстовой сцены в 1,5 раза дороже прямой
отрисовки. Известная составляющая — строка, пересекающая ~4 тайла, проходит
per-rune цикл в каждом (отсечка в `drawTextWithFont` отбрасывает глифы
только правее клипа); точная доля не профилирована. Для 4а: раскладка строки
один раз на команду (позиции глифов в команде), тайл блитит только свои
глифы.

### Масштабирование по числу воркеров

`go test -cpu N` (пул воркеров стартует с GOMAXPROCS = N), `-count=5`,
кадр «запись + растр» текстовой сцены с личными видами шрифта против
`RenderFrameFull` того же прогона:

| Воркеров | Прототип, запись + растр | Только растр | Сегодня |
|---|---|---|---|
| 1 | 4,67 мс | 4,33 мс | 3,61 мс |
| 2 | 3,01 мс | 2,66 мс | 3,09 мс |
| 4 | 1,95 мс | 1,54 мс | 2,76 мс |
| 8 | 1,33 мс | 1,10 мс | 2,63 мс |
| 12 | 1,11 мс | 0,74 мс | 2,65 мс |
| 20 | 0,63 мс | 0,38 мс | 2,02 мс |

Абсолютные числа этой серии примерно на треть выше основного прогона
(состояние машины во время серии; `RenderFrameFull` при одном процессоре
ещё и теряет параллельный дифф) — сравнивать внутри строки: прототип
обгоняет с 4 воркеров (×1,4), на 8 — ×2,0, на 12 — ×2,4, на 20 — ×3,2.
Запись (~0,27 мс) идёт одной горутиной и ограничивает выигрыш снизу
(закон Амдала); с удержанием списков у виджетов (Р5 целиком) в полный кадр
по `Invalidate` она входит всё равно — все виджеты перерисовываются.
Рабочий стол с размытием масштабируется хуже: сегмент `BlurBehind` и копии
тайлов в рабочий буфер — последовательная часть (см. ореол ниже).

### Кадр без изменений (Р7)

| | Сегодня | Прототип |
|---|---|---|
| 1280×800, кадр без изменений вне on-demand (`RenderFrameNoChange`: фон + дерево + дифф) | 2,16 мс | **7,1 мкс** (`ProtoNoChange_Text`): раскладка 182 команд по 260 тайлам и сравнение хэшей, пул не трогается |
| Full-HD, только дифф без изменений (`DiffFullNoChange`) | 90–270 мкс (шумный) | 9,8 мкс (`ProtoNoChange_TextFullHD`, 510 тайлов) |
| Full-HD с повторной записью команд (без удержания списков) | 2,16 мс (кадр целиком) | 282 мкс (`ProtoNoChangeRecord_TextFullHD`) |

Р7 подтверждён: «единицы микросекунд» при удержанных списках (Р5), ~0,3 мс
без удержания — всё равно в 7 раз дешевле сегодняшнего кадра без изменений.
В on-demand режиме кадр без изменений у обеих моделей не рендерится вовсе.
**Оговорка:** в кадре с читающей командой Р7 в стенде не действует (все
тайлы сегментов рисуются), см. «Кадр рабочего стола с размытием».

### Частичное изменение

| | Сегодня | Прототип |
|---|---|---|
| Один лейбл из 180, 1280×800 (`RenderFramePartial`: `InvalidateRect` + пропуск поддеревьев + дифф по damage) | 27,7 мкс | 40,8 мкс (`ProtoPartialRetained_Text`): команда меняется в удержанном списке (охват пересчитан), перераскладка всех 182 команд по 260 тайлам (≈7 мкс), два тайла растрятся и сравниваются |
| то же с полной повторной записью | — | 372 мкс (`ProtoPartial_Text`) |

Частичный кадр сегодня уже дёшев; прототип проигрывает ~13 мкс. Из 40,8 мкс
раскладка стоит ≈7 (`ProtoNoChange_Text`), остальное — растр двух тайлов с
полным per-rune циклом строки и накладные пула. Инкрементальная раскладка
(виджет снимает свои прежние команды с тайлов и кладёт новые) в стенде не
реализована и не измерена; вместе с раскладкой строки на команду она —
условие, при котором частичный кадр не хуже сегодняшнего.

### Кадр рабочего стола с размытием (главный сценарий простоя)

Сегодня тик часов (`Pipeline_ClockTick`) стоит 0,52 мс: пропуск поддеревьев
и дифф по damage. В стенде любой кадр с `BlurBehind` — сегментный: без Р7 и
Р8, с полным диффом — 1,29–1,37 мс (`ProtoTiled_Desktop`,
`ProtoRecordTiled_Desktop`), то есть **в 2,5 раза дороже сегодняшнего**
тика часов, пока размытие идёт с барьером. Это главный риск модели для
WinLine: акриловая панель задач рисует размытие каждый кадр.

### Запись команд (Р5)

| Сцена | Запись кадра | На команду |
|---|---|---|
| Текст, 182 команды | 282 мкс | 1,5 мкс — почти целиком измерение строки для охвата (`MeasureTextFont` + метрики) |
| Рабочий стол, 159 команд | 47 мкс | 0,3 мкс |

Запись дешевле отрисовки в 7–55 раз; у текста охват дешевле брать из
границ виджета или считать по раскладке, которую команда всё равно будет
хранить (не измерено).

### Память (Р8)

| Разрешение | Сегодня (front + back) | Стенд (front + холсты воркеров, front+back по 16 КБ) | Цель 4а (воркер без front) |
|---|---|---|---|
| 1280×800 | 8,2 МБ | 4,1 МБ + 21 × 32 КБ | 4,1 МБ + 21 × 16 КБ |
| Full-HD | 16,6 МБ | 8,3 МБ + 0,7 МБ | 8,3 МБ + 0,3 МБ |
| 4K | 66 МБ | 33 МБ + 0,7 МБ | 33 МБ + 0,3 МБ |

При личных видах шрифта — плюс L1-кэши `FontCache` на воркер. Выполняется
для кадров **без читающих команд**; с `BlurBehind` стенд заводит рабочий
буфер — буферов три (front, work, тайлы), экономия теряется.

Выход для 4а — «ореол»: тайл под слоем размытия рисует команды сегмента в
(64 + 2h)×(64 + 2h), h — охват ядра размытия, и берёт подложку из своего
растра; барьер и рабочий буфер исчезают. Цена: панель задач Windows 11 —
высота 48 px, радиус 22 (`theme/profiles.go`), при 800 px занимает два ряда
тайлов (40 из 260); множитель площади (64 + 2·22)²/64² = 2,85, при двух
проходах box-blur охват ядра до 2r — до 4,9; итого **+28…+60 % к работе
кадра** рабочего стола, зато тик часов получает Р7 и Р8. Ореол меняет
пиксели у стыков: сетка уменьшения ×4 и охват ядра в `backdrop.go`
привязаны к области размытия, а не к тайлу, — тождественность с сегодняшним
размытием не гарантирована, golden-эталоны с акрилом потребуют регенерации.
Ореол и кэш размытия прототипированы (раздел «Три варианта размытой
подложки» ниже): оба побайтно равны движку, оценка выше оказалась
завышенной — ореол обрезается кадром и дорог только на тайлах под слоем.

## Три варианта размытой подложки (дополнение по запросу владельца)

Стенд `engine/renderproto_blur_test.go`: все три варианта реализованы и дают
кадр рабочего стола, **побайтно равный** кадру движка
(`TestRenderProto_BlurVariantsMatchDirect`); снимки панели задач и карты
расхождений — `TestRenderProto_BlurVariantsImages` (`PROTO_OUT=каталог`).

| Вариант | Как устроен |
|---|---|
| A. Барьер | кадр делится на сегменты по читающей команде; размытие — на полном рабочем буфере; тайлы сегментов рисуются все, дифф полный; Р7 и Р8 не действуют |
| B. Ореол | тайл под слоем размытия рисует команды кадра в холст с запасом h по периметру (h = 52 px при радиусе 22: два прохода box-blur радиусом 5 на подложке, уменьшенной в 4 раза, плюс неполные блоки; кратен 4 — сетка уменьшения совпадает с движком) и размывает сам; ореол **обрезается кадром**: движок зажимает подложку краем кадра, и холст ореола обязан зажимать её там же — без этого нижний ряд тайлов читал пустоту за краем, и панель шла пятнами (до 55 по каналу); хэш тайла под размытием считается по командам в пределах ореола |
| C. Кэш размытия | результат `BlurBehind` хранится по ключу из самой команды и команд под ней в области чтения; пока содержимое под слоем не менялось, команда заменяется блитом готового растра, и кадр идёт без читающих команд (Р7 и Р8 действуют); промах — команды под слоем рисуются в холст размером с область чтения, там же размытие тем же кодом |

Цены (20 CPU, `-count=8`, один прогон; с записью команд):

| Сценарий | Сегодня | A. Барьер | B. Ореол | C. Кэш |
|---|---|---|---|---|
| Полный кадр рабочего стола (`Pipeline_FullFrame`) | 2,53 мс | 1,42 мс | 0,75 мс | 0,43 мс при попадании; при промахе — как «изменение под размытием» |
| Тик часов (`Pipeline_ClockTick`; у прототипа — строка часов в удержанном списке) | 0,55 мс | 1,31 мс (×2,4 хуже) | 0,13 мс (×4,4 лучше) | 0,08 мс (×6,5 лучше) |
| Изменение под размытием (полоса обоев под панелью; окно тащат под ней) | ≈ `Pipeline_WindowDrag` 1,65 мс | 1,28 мс | 0,55 мс | 1,13 мс (промах: область чтения 1280×92 заново + размытие) |

Тайлов за тик: барьер — 520 (все, два сегмента), ореол и кэш — 4 (тайлы
строки часов), грязных 2.

Подводные камни:

- **A. Барьер.** Любой кадр с размытием — без Р7 и Р8: тик часов в 2,4 раза
  дороже сегодняшнего, буферов снова два. Зато ни одного допущения о
  локальности размытия.
- **B. Ореол.** (1) Край кадра и клипа: подложка обязана зажиматься ровно как
  в движке — первая реализация давала пятна. (2) Цена растёт с радиусом:
  холст ореола (64 + 2h)² — при радиусе 22 это 6,9 площади тайла, при 40 —
  около 15; флайауты с большим радиусом дороже панели. (3) Хэш тайла под
  размытием включает соседей в пределах ореола: окно, подъехавшее к панели,
  перерисовывает её тайлы — верно, но дороже. (4) Слои друг над другом
  (флайаут с акрилом над акриловой панелью) требуют ореола на сумму радиусов;
  в стенде учитывается только верхний уровень команд, группа
  `DrawWithOpacity` с размытием внутри не разобрана. (5) Размытие в каждом
  тайле заводит свои буферы (158 КиБ на полный кадр) — в реализации нужны
  scratch-буферы воркера. (6) Холсты ореола разных размеров у краевых тайлов —
  пул по размеру.
- **C. Кэш размытия.** (1) Ключ обязан покрывать всё, что под слоем: команды,
  пересекающие область чтения; с удержанными списками виджетов это
  естественно, а заниженный охват команды даёт устаревшее размытие.
  (2) Промах стоит как барьер (1,13 мс): видео или окно, движущееся под
  панелью, возвращают цену барьера на каждый кадр. (3) Память: растр на
  каждый слой (панель 1280×48 — 245 КиБ) и политика вытеснения — в стенде ключи
  копятся. (4) Как и у ореола, группы с размытием внутри не разобраны.
  (5) Блит вместо размытия должен сохранить классификацию областей для
  кодека (`Regions`: размытая подложка — картинка) и клип, в том числе
  скруглённый, самой команды.

Вывод: сами по себе B и C лучше A во всех сценариях, а их слабые места
дополняют друг друга — кэш дёшев, пока под слоем ничего не меняется, ореол
дёшев именно при изменениях под слоем. **Рекомендация к 4а — кэш с ореолом на
промахе**: тайл под размытием при промахе кэша рисует ореолом (0,55 мс вместо
1,13), при попадании блитит растр (0,08 мс на тик). Барьер остаётся только
для `Snapshot`.

## Команды, читающие пиксели

Из `core/draw` и их вызовов в репозитории:

| Команда | Что читает | Где зовётся | В тайловой модели |
|---|---|---|---|
| `BlurBehind(r, radius, tint)` | кадр под слоем с запасом `radius` | `widget/backdrop_material.go` (acrylic, mica-fallback), `desktop/paint.go` (панели рабочего стола), `popupcontext` (попапы) | барьер (стенд) или ореол (4а) |
| `Snapshot(r)` | кадр в `r`, синхронно внутри `Draw` | `widget/dockmanager.go` (призрак перетаскиваемой панели) | **не прототипирован**: при Р5 в момент `Draw` кадр ещё не растрён, барьер вернуть снимок не может; нужен другой механизм — снимок прошлого `front` или отложенная команда «снимок → буфер» |
| `DrawNoise(r, amount)` | свои пиксели, зерно по координатам холста (`noise.go`) | `backdrop_material.go`, `desktop/paint.go` (acrylic Windows 10) | в холсте воркера координаты локальные — зерно другое; в стенде идёт сегментом; для 4а — шум с заданным началом координат |
| `DrawWithOpacity(r, a, draw)` | область до и после `draw` | `widget/popupmenu.go` (проявление подменю), `desktop/flyout.go` | внутри тайла, группа целиком; `BlurBehind` внутри группы (флайаут с акрилом) тянет сегмент за собой |
| `FillRectAlpha`, AA-фигуры, текст, `DrawImage*`, `BlitPixels*` | пиксель назначения для смешения | везде | внутри тайла |
| `MicaBehind` | источник обоев, не кадр | `backdrop_material.go` | внутри тайла; холсту воркера обои отдаются наследованием (`InheritWallpaper`), как буферу попапа |
| `BlitPixels*` с буфером, переписываемым на месте (`ExternalSurface`: окно программы, видео) | — | `widget/externalsurface.go` | хэш по адресу буфера изменения не видит: нужен счётчик поколения буфера в команде (у `ExternalSurface` есть damage/`Update`); в стенде поколение ведётся только для `InvalidateImageCache` |

## Что не измерено и риски

- HiDPI: обе сцены на масштабе 1; раскладка по тайлам в физических
  пикселях при дробном масштабе требует охвата в физических координатах.
- Попапы хоста, модальные слои, переходы оверлеев, переносы (`MoveRegion`),
  `Regions` для кодека в стенд не входят; в тайловой модели классификация
  тайлов становится точной по командам — довод за Р5.
- Удержание списков у виджетов (Р5 целиком) и инкрементальная раскладка не
  прототипированы; все «удержанные» измерения — на готовом списке кадра.
- `Snapshot` не прототипирован; группы `DrawWithOpacity` с размытием внутри
  в вариантах B и C не разобраны (только верхний уровень команд).
- Охват текста в стенде — шаги пера с запасом в полкегля; при раскладке
  строки на команду охват берётся по маскам.
- Паника виджета в `Draw` при записи не портит кадр (ничего ещё не
  нарисовано) — довод Р5 подтверждён конструкцией, тестом не покрыт.

## Рекомендация к этапу 4а

Принять Р5–Р8 с условиями, которые прототип выявил:

1. Воркеру — свой вид шрифта (личный L1 над общим L2 кэша 4.2) с тем же
   составом шрифтов, что у холста. Без этого Р6 не даёт выигрыша.
2. Текст — одна раскладка на команду (позиции глифов внутри команды), тайл
   блитит только свои глифы; шум — с началом координат кадра; у буферов и
   картинок — поколение в команде.
3. Раскладка по тайлам — инкрементальная по виджету.
4. `BlurBehind` — кэш размытия с ореолом на промахе вместо барьера (см.
   «Три варианта размытой подложки»: оба побайтно равны движку); `Snapshot`
   — снимок прошлого `front` или отложенная команда.
5. Критерии приёмки — существующие бенчмарки, числа по стенду: полный
   текстовый кадр (`RenderFrameFull`) ≤ 0,65 мс; полный кадр рабочего стола
   (`Pipeline_FullFrame`) ≤ 1,4 мс; кадр без изменений с удержанными
   списками (`RenderFrameNoChange`) ≤ 10 мкс; частичный кадр
   (`RenderFramePartial`) и тик часов (`Pipeline_ClockTick`) — не хуже
   сегодняшних (28 мкс и 0,52 мс) — это требование к инкрементальной
   раскладке и ореолу, стендом не подтверждённое.
