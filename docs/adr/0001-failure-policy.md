# ADR-0001. Политика сбоев: паника в виджете не роняет процесс

Статус: принято 2026-10-26, ветка `feature/engine-architecture`, работы к 4.0
(этап 1, задача 1.2). Основание — `docs/ARCHITECTURE_REVIEW_RU.md`, §6.

## Контекст

До этого решения в `engine` и `window` не было ни одного `recover`. Паника в
`Draw` или обработчике одного виджета раскручивала горутину кадра и
завершала процесс. Для самостоятельной программы это потеря несохранённой
работы, для `winline-session` — конец сеанса пользователя, для `winlined` с
общим процессом — отказ всех сеансов сразу. Движок — основа оболочки, и
граница отказа должна проходить по виджету, а не по процессу.

Одновременно тесты репозитория (`tests/engine_test.go`,
`tests/anim_widgets_test.go` и другие) проверяют, что движок «не паникует»:
им нужна паника, которая долетает до `testing`.

## Решение

### Политика

```go
type FailurePolicy uint8
const (
    FailureIsolate   FailurePolicy = iota // паника ловится, виджет помечается, процесс живёт
    FailurePropagate                      // как раньше: паника идёт дальше
)
func (e *Engine) SetFailurePolicy(p FailurePolicy)
func (e *Engine) FailurePolicy() FailurePolicy
func (e *Engine) SetOnPanic(fn func(PanicInfo))
```

**По умолчанию `FailureIsolate`.** Исключение одно: под `go test`
(`testing.Testing()` истинно) движок создаётся с `FailurePropagate`, чтобы
тесты видели паники как прежде. Тест, проверяющий изоляцию, ставит
`FailureIsolate` явно. Это единственное место, где поведение движка зависит
от того, тест это или нет, и оно документировано.

При `FailurePropagate` функция `recover` не вызывается вовсе: паника
продолжается с исходным стеком, как в 3.x.

### Границы, где стоит `recover`

| Граница | Где | Что после паники |
|---|---|---|
| Отрисовка кадра | `renderFrame`: от `beginDrawContract` до диффа (дерево, оверлеи, модалки, хостовые попапы, подсказка) | кадр не отдаётся; следующий кадр полный (`fullNext`); если виджет известен — помечен сломанным |
| Очередь `Post` | каждая функция по отдельности (`runPosted`) | остальные функции очереди выполняются |
| Таймеры `After`/`Every` | `Timer.fire`, вокруг `fn` | `Every` продолжает идти |
| Тики анимаций | вызов `widget.StepAnimationsFor` из цикла | пакет `widget` снимает признак «шагаю» и прокидывает панику дальше, иначе анимации этого движка замерли бы навсегда |
| Ввод | `SendKeyEvent`, `SendMouseMove`, `SendMouseButton`, `SendMouseWheelPixels`, `SendMouseWheelRaw`, `SendTouch`, `SendFilesDropped`, `SendPointerLeave`, `ActivateAccessible`, `AccessAction`; IME идёт через `Post` | захват мыши снимается (`ReleaseCapture`), `pressConsumer` сбрасывается; фокус не трогается |
| Потребитель кадров | `deliver`, вокруг `FrameSink.Present` | кадр считается отданным; канал получает его как обычно |

Насос окна ОС (`window`) и бэкенды — отдельная граница, этап 9.

### Сломанный виджет

Паника в `Draw` называет виджет, только если включён учёт рисующихся
(`widget.EnableDrawTrace`, тот же, что у проверки контракта). Держать его
включённым всегда дорого, поэтому:

1. первая паника в `Draw` при выключенном учёте — движок включает учёт и
   запрашивает полный кадр;
2. повторная паника называет виджет; движок помечает его
   (`widget.MarkBroken`), выключает учёт, снова запрашивает полный кадр;
3. сломанный виджет больше не рисуется: на его месте заглушка (серый
   прямоугольник с рамкой), его оверлеи не рисуются; события до него
   доходят, и паника в обработчике ловится той же границей ввода;
4. `widget.ClearBroken(w)` возвращает виджет к жизни (после правки
   состояния программой), `widget.BrokenWidgets()` перечисляет сломанные.

О каждой панике `SetOnPanic` получает `PanicInfo{Where, Widget, Path, Value,
Stack}`; без обработчика пишется `log.Printf` — один раз на пару «место +
виджет», остальные считаются в `Stats.Panics`.

### Чего решение не делает

- Не прерывает «зависший» виджет: Go не умеет остановить горутину. Сторож
  длительности кадра — отдельная задача.
- Не закрывает модальный диалог, чей `Draw` паникует: на его месте
  заглушка, Escape доходит до его обработчика. Программа закрывает его
  сама (`CloseModal`).
- Не восстанавливает состояние самого виджета: что он успел изменить до
  паники, остаётся.
- Не защищает `window`: паника в насосе ОС по-прежнему валит процесс до
  этапа 9.

## Последствия

- Совместимость: единственное наблюдаемое изменение для программ — процесс
  не падает. `SetFailurePolicy(engine.FailurePropagate)` возвращает прежнее.
- Стоимость: по одному `defer` на кадр, на функцию очереди, на событие
  ввода; на горячем пути отрисовки — одна атомарная проверка на ребёнка,
  общая с учётом рисующихся. Бенчмарки этапа 0 — в пределах шума.
- `Stats.Panics` считает все пойманные паники.
